# v1.1B Governed Federation Design

Status: approved for local implementation  
Baseline: `docs/V1_1_CAPABILITY_BASELINE.md`

## Purpose

Add optional team collaboration without weakening Rta-Smriti's defining
properties: local ownership, append-only provenance, bitemporal truth,
contradiction retention, explicit authority, abstention, and operator control.
Federation shares selected memory and evidence; it does not execute project
work, choose models, orchestrate tools, or become an agent runtime.

## Research Basis

- [Local-First Software](https://www.inkandswitch.com/essay/local-first/)
  establishes offline operation, local primary copies, ownership, longevity,
  and collaboration as joint requirements.
- [Keyhive](https://www.inkandswitch.com/keyhive/notebook/) shows that
  authorization must travel with data in a local-first system and that
  revocation is a temporal, causally ordered state transition.
- [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) provides useful group
  and epoch semantics: membership changes advance an epoch and removed members
  do not receive fresh epoch secrets. v1.1B does not claim MLS compatibility.
- [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html) defines HPKE. The
  installed `cryptography` dependency provides its X25519, HKDF-SHA256, and
  AEAD implementation, avoiding custom public-key envelope cryptography.
- [Automerge sync](https://automerge.org/automerge/automerge/sync/index.html)
  demonstrates efficient local-first exchange, while Rta-Smriti retains its
  own domain-specific event semantics instead of making the full database a
  generic CRDT.
- [SQLite sessions](https://www.sqlite.org/sessionintro.html) can capture
  changesets, but the extension is not enabled in many standard Python/SQLite
  builds. It is therefore not a portable v1.1B dependency.
- [Syncthing relay protocol](https://docs.syncthing.net/specs/relay-v1.html)
  demonstrates the correct relay boundary: forwarding infrastructure need not
  understand protected application traffic.

## Considered Architectures

### Full MLS group protocol

Strong group key evolution and post-compromise properties, but excessive for
the first federation release without a mature, portable Python MLS dependency.
Implementing MLS directly would create unacceptable cryptographic risk.

### Encrypted database or snapshot exchange

Simple transport, but coarse sharing, weak offline conflict semantics, large
retransmission, and no clean preservation of per-event provenance or
authorization. Rejected.

### Selected: signed events plus scoped epoch keys

Replicate immutable domain events. Each event is signed by its author and
encrypted with a content key for one opaque protection scope. Scope keys are
distributed to authorized peers through HPKE envelopes and rotated when access
changes. An untrusted relay stores content-addressed ciphertext only.

This is intentionally smaller than MLS. It borrows epoch semantics but makes
no forward-secrecy or post-compromise-security claim beyond the tested key
rotation boundary.

## Trust And Privacy Model

1. The local brain is authoritative for the operator's accepted state.
2. Peer public keys identify devices, not verified real-world people.
3. Invitations transfer public identity, allowed scopes, and sealed key
   envelopes. Human identity verification stays outside the protocol.
4. Relay infrastructure is untrusted for confidentiality, integrity, ordering,
   availability, and completeness.
5. Relay-visible metadata includes opaque space/scope identifiers, recipient
   key fingerprints, ciphertext sizes, and traffic timing. This leakage is
   documented rather than hidden.
6. A compromised authorized device can read material it legitimately received.
   Revocation protects future epochs; it cannot erase prior plaintext or
   copies.
7. Mutually untrusted processes under one OS account remain outside the local
   storage threat boundary.

## Cryptographic Profile

- Device signing key: Ed25519.
- Device envelope key: X25519.
- Peer key distribution: RFC 9180 HPKE base mode through `cryptography`.
- Event encryption: ChaCha20-Poly1305 with a random 96-bit nonce.
- Scope content keys: random 256-bit keys, one active key per scope epoch.
- Canonical encoding: bounded UTF-8 JSON with sorted keys and no insignificant
  whitespace.
- Digests and content addresses: SHA-256.

Private identity keys use encrypted PKCS8 files protected by an operator
passphrase or private passphrase file. The database stores public keys and
sealed scope-key envelopes, never plaintext private keys or plaintext scope
keys. Decrypted keys remain process-memory values only.

## Protection Scopes

Per-memory permissions are cryptographic protection scopes rather than labels
over one shared key:

- `local`: never enters federation.
- `team`: available to all active members granted the scope.
- `review`: available only to explicitly named reviewer peers.
- custom opaque scopes: created by an owner for a bounded peer set.

A memory or collaboration event belongs to exactly one scope. Moving material
to a broader scope creates a new explicit event and requires operator approval;
it never silently mutates the original event.

## Event Envelope

The relay-visible header contains only protocol data:

```json
{
  "schema": "rta-smriti.federation-event/v1",
  "space_id": "opaque-id",
  "scope_id": "opaque-id",
  "epoch": 3,
  "event_id": "sha256-of-canonical-signed-envelope",
  "author_peer_id": "public-key-fingerprint",
  "author_sequence": 42,
  "parents": ["event-digest"],
  "nonce": "base64",
  "ciphertext": "base64",
  "signature": "base64"
}
```

Event type, project identity, object identity, content, comments, decisions,
timestamps beyond protocol ordering, and provenance details remain encrypted.
The signature binds the complete header except `signature`, including the
ciphertext digest and causal parents.

## Event Types

- memory assertion, correction, supersession, and tombstone;
- evidence attachment and evidence-status transition;
- comment and review request;
- approval proposal, approval decision, and decision withdrawal;
- scope creation and membership grant;
- peer invitation, acceptance, suspension, revocation, and re-admission;
- epoch rotation and key-envelope publication;
- recovery declaration and device replacement;
- synchronization checkpoint and explicit conflict acknowledgement.

All are immutable. Editable views are materialized projections.

## Authorization

Authorization is evaluated at the event's causal frontier, not against only the
receiver's latest wall-clock state. Membership and capability events form an
append-only authorization ledger. A received event is applied only when:

1. its envelope and canonical bounds are valid;
2. its digest and Ed25519 signature verify;
3. its peer and author sequence are valid and not replayed;
4. all declared parents are present and valid;
5. the author held the required capability for that scope and event type at
   the causal frontier; and
6. its scope key was legitimately available for that epoch.

Invalid, unauthorized, ambiguous, and dependency-incomplete events are
quarantined with bounded reason codes. Diagnostics never reveal decrypted
content from unauthorized scopes.

Authorization gates run before:

- ingestion or projection into searchable state;
- retrieval and progressive evidence expansion;
- context compilation;
- outbound synchronization;
- bundle export; and
- diagnostics or support artifacts.

## Deterministic Reconciliation

The replicated structure is a grow-only set of authenticated events plus
explicit revocation, supersession, and tombstone events. Peers exchange event
digests and missing immutable envelopes. Identical event IDs deduplicate;
different bytes under one claimed ID are tampering.

Events are projected in deterministic causal order. Ready events are ordered
by causal depth, author sequence, author fingerprint, and event ID. Missing
parents stay pending. Concurrent assertions remain concurrent versions.
Rta-Smriti never resolves project truth by last-writer-wins.

Domain rules:

- bitemporal claims preserve valid time and transaction time;
- conflicting claims remain disputed until an authorized decision event;
- comments append and do not overwrite;
- approval proposals and decisions retain every vote and rationale;
- concurrent incompatible membership changes create a blocking governance
  conflict for explicit owner resolution;
- imported evidence retains original author, signature, source event, and
  receiving decision.

## Storage Model

Schema v12 adds narrowly scoped tables:

- `federation_identities`: public device identity and protected key references;
- `federation_spaces`: local project binding and collaboration state;
- `federation_scopes`: opaque protection scopes and current epochs;
- `federation_scope_epochs`: immutable rotation receipts without plaintext keys;
- `federation_peers`: public keys, fingerprints, status, and local labels;
- `federation_capability_events`: append-only grants and revocations;
- `federation_key_envelopes`: HPKE-sealed scope keys per peer and epoch;
- `federation_events`: immutable encrypted envelopes and validation state;
- `federation_sync_cursors`: transport-specific receipt cursors, never truth;
- `federation_quarantine`: bounded invalid or incomplete envelope metadata;
- `federation_projections`: rebuildable links to local truth/memory records.

Database triggers reject updates and deletes to immutable federation records.
Derived cursors and projections may be rebuilt after validation.

## Transport Interface

```python
class FederationTransport(Protocol):
    def advertise(self, space_id: str, digests: Sequence[str]) -> Receipt: ...
    def list_missing(self, space_id: str, known: Sequence[str]) -> Sequence[str]: ...
    def put(self, space_id: str, event_id: str, envelope: bytes) -> Receipt: ...
    def get(self, space_id: str, event_id: str) -> bytes: ...
```

The first implementation is a bounded filesystem relay used for two-brain
proof and offline recovery. The optional self-hosted HTTP relay follows the
same immutable blob contract. It has quotas, rate limits, bearer-independent
opaque space capabilities, and no decryption or project logic.

## Operator Interface

CLI and MCP expose preview-first operations with matching semantics:

- identity create, inspect, back up, and replace;
- space create, status, pause, resume, and remove locally;
- invitation preview, issue, inspect, accept, reject, and expire;
- scope create, grant, revoke, and rotate;
- sync preview, push, pull, verify, and repair;
- conflict inspect and explicitly resolve;
- signed/encrypted review-bundle preview, export, import, and verify;
- device-loss recovery with an honest statement of lost capabilities.

The dashboard presents local-only, offline, healthy, partial, pending-parent,
conflict, revoked, tampered, key-missing, relay-unavailable, and recovery states.
No collaboration feature is enabled during ordinary single-user operation.

## Migration And Compatibility

- Opening schema v11 for inspection never migrates it.
- v11 to v12 requires the existing supervisor's preview, private backup,
  explicit approval digest, atomic migration, validation, and rollback path.
- A v11 runtime refuses a v12 brain with upgrade guidance and no mutation.
- Disabling federation leaves all local-only interfaces usable.
- Removing a local federation enrollment does not delete accepted local truth.
- Wire schema v1 is versioned independently of SQLite schema v12.

## Performance Budgets

- Disabled federation: no material regression against the frozen local
  benchmark and performance ceilings.
- Envelope validation: p95 below 5 ms for a 16 KiB event on the release Windows
  baseline; separately recorded on hosted Linux and macOS.
- Reconcile 10,000 already-downloaded synthetic events: below 10 seconds and
  below 256 MiB peak process memory on the release baseline.
- Incremental no-change sync: below 250 ms excluding transport latency.
- Relay reads and writes are bounded by count, encoded bytes, decoded bytes,
  nesting, and wall time.

These are regression budgets, not universal latency claims.

## Non-Goals For v1.1B

- MLS interoperability or claims of MLS-level PCS/forward secrecy;
- verified human identity or enterprise directory integration;
- real-time collaborative document editing;
- automatic trust, autonomous sharing, or silent conflict resolution;
- cloud-hosted managed service, billing, or telemetry;
- agent execution, model routing, tool orchestration, or repository mutation.

## Release Exit

v1.1B is releasable only when every acceptance item in the Decade Ahead goal
has a reproducible test or named operator receipt, all claims match evidence,
and the exact public candidate passes privacy, security, supply-chain,
cross-platform, migration, rollback, browser, and package gates.
